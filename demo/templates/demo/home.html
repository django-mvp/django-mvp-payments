{% extends "page_view.html" %} {% block page.content %} Django has no shortage of packages that talk to a payment provider. What none of them give you is the part your users look at. A package hands you a subscription record, a list of prices and an endpoint that starts a checkout, and leaves the plan grid, the subscribe button, the billing panel and the card-expiring notice to be built from raw utility classes — in every project, every time. This package is that layer, plus a small Stripe app that keeps each user's subscriptions in step with Stripe. It runs no payment logic and depends on no third-party payment backend. Install it with the Stripe app and its pages turn up in django-mvp's Account Center, rather than leaving you to build and route them. A component names the provider it speaks to. <c-stripe.pricing-table> is Stripe's own pricing table, and the stripe.subscription page reads the records of this package's Stripe app. A second provider would get a namespace of its own beside it rather than underneath it. There is no neutral component that renders through a swappable backend. An interface across payment libraries can only offer what they have in common, and subscription models genuinely differ — it fits the first library, bends for the second and is a liability by the third. A namespace per backend costs some duplication and buys the freedom to match each one exactly. Your backend's own records, rendered as daisyUI markup. It themes with the rest of the site and can show a person their own state — which plan they are already on, what they cannot buy, what happens at the end of the period. A thin wrapper around the drop-in the provider already publishes, such as Stripe's pricing table. Faster where there is no signed-in person to reflect, and configured in the provider's dashboard rather than here. Neither is the fallback for the other. No API calls from Python, no webhook handling, no card data, no secrets and no money moving anywhere. Those belong to the payment backend, they are genuinely hard to get right, and a presentation layer has no business having an opinion about them. There are no models, no migrations, no forms, no admin and no serializers either. A page here has whatever view it needs, built on django-mvp's own view classes, and every value on it was decided by the backend or by the project installing this. This is the same <c-stripe.pricing-table> component the Account Center's Plans page renders — placed here, on this landing page, with nothing behind it but its own two attributes. There is no view of ours behind this page and no sign-in requirement, and the component needs neither. Every project starts here: nothing supplied, or the provider's library never loaded. Both states are one click away rather than left to be imagined. The package's own Plans page, reached with neither a pricing table id nor a publishable key supplied: Both values configured, the mount point rendered, and the provider's own script never loaded: The user subscriptions page is built: sign in and open the Account Center to see it, under Billing. It carries the way to the plans page, which is routed and waiting on its own roadmap item. This page runs on the demo project in the repository. It is a demonstration target and is never deployed — the theme switcher in the sidebar is here so a component can be looked at under more than one theme as it is built. {% endblock page.content %}
