{% extends "page_view.html" %} {% load mvp_payments %} {% block page.content %} Django has no shortage of packages that talk to a payment provider. What none of them give you is the part your users look at. A package hands you a subscription record, a list of prices and an endpoint that starts a checkout, and leaves the plan grid, the subscribe button, the billing panel and the card-expiring notice to be built from raw utility classes — in every project, every time. This package is that layer, plus a small Stripe app that keeps each user's subscriptions in step with Stripe. It runs no payment logic and depends on no third-party payment backend. Install it with the Stripe app and its pages turn up in django-mvp's Account Center, rather than leaving you to build and route them. A component names the provider it speaks to. <c-stripe.plans> draws the prices in Stripe's catalogue, and the stripe.subscription page reads the records of this package's Stripe app. A second provider would get a namespace of its own beside it rather than underneath it. There is no neutral component that renders through a swappable backend. An interface across payment libraries can only offer what they have in common, and subscription models genuinely differ — it fits the first library, bends for the second and is a liability by the third. A namespace per backend costs some duplication and buys the freedom to match each one exactly. No API calls from Python, no webhook handling, no card data, no secrets and no money moving anywhere. Those belong to the payment backend, they are genuinely hard to get right, and a presentation layer has no business having an opinion about them. There are no models, no migrations, no forms, no admin and no serializers either. A page here has whatever view it needs, built on django-mvp's own view classes, and every value on it was decided by the backend or by the project installing this. These are the plans the plans page shows, placed here on this landing page with one template tag and one component.
